## Evidence plan and limits

Nine new real Production HTTP/RS256/normal-DI PostgreSQL cases cover all three create routes and both update routes. Negative writes compare complete users from both stores plus create receipts, recovery effects, challenges and sessions. Direct-service invalid names/email and new duplicate-create conflicts are checked too; a separately seeded invalid-username legacy receipt uses independent fixed Pascal-case JSON PBKDF2 evidence and must replay200 without changing any store, while a changed payload conflicts409. Positive creation proves a real hash and normalization; updates cover different-owner username/email, same-owner casing, permitted punctuation, preserved hash/ID/counter and rotated stamps, missing404 and no recovery effects. The opt-in update fixture enables real recovery options and removes only the background worker for deterministic observation; middleware, authentication, services and database writes remain normal. Existing worker and recovery suites still run.

No schema change, unique-email index, new cross-row serializable guarantee, SDK UserManager/provider replacement, Web registration policy expansion, universal user-validation closure or original data migration is claimed. The original check-before-write duplicate-email and concurrent username collision checks across different target rows are not serialized by this slice; no universal collision-race guarantee is claimed. No consumer edits; inspected accepted Intranet3be71d and bounded Customer/Employee callers use create routes, while no update caller was found in those inspected heads. Static source review and diff checks only so far; Release0W/E, full suite, focused9 plus reset4, raw coverage, all prior foci and static gates are required in hosted Ubuntu before acceptance.

See identity-administration-version-contract.md for the additive safe projection/versioned-write contract. Existing ordinary PUT stays compatible; the new explicit versioned route requires If-Match and cannot silently overwrite a stale edit.
