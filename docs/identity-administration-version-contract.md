# Safe identity projection and versioned administration

Producer candidate on accepted PR147 main26c91358f9c0a615d6052a27e5be5369e747520d (fresh main37406133762:767 passed). The new producer behavior has no hosted acceptance or consumer release yet. Existing ordinary CRUD routes and safe editable DTO fields remain intact.

GET /auth/v1/{customer|employee}-identities/{databaseId} retains the safe identity projection and adds `version`, an opaque uppercase64-hex SHA256 digest over the immutable identity ID plus current concurrency stamp, separated by NUL. The same digest is returned as a quoted strong ETag. It is an edit-version token, not an authorization token. PasswordHash, SecurityStamp, ConcurrencyStamp, normalized names/emails and operation receipts are never projected. No secrets or signing keys are introduced.

New PUT /auth/v1/{customer|employee}-identities/{databaseId}/versioned accepts the EXISTING update JSON and an exact quoted strong If-Match header. The existing update permission and LegacyEmployee policy are mandatory. Missing/blank version returns generic428; missing identity with a supplied header returns404; stale, wildcard, weak or otherwise mismatched version returns generic412; invalid fields or another owner's normalized username/email returns generic400; valid matching update returns204. Employee recovery disabled/pending-receipt state still returns503. The unversioned PUT remains compatible. The projection's raw business ID cannot be changed through either update request.

Customer versioned update reads without tracking and performs one conditional SQL update by immutable identity ID and the observed concurrency stamp. Zero affected rows returns412, including a concurrent replacement/deletion/credential/accounting change. Only existing permitted fields plus fresh security/concurrency stamps are changed; hash, identity/business IDs and failed counter stay untouched. ONLY conditional operations use fresh same-store contexts cloned from normal options, with NonRetryingExecutionStrategy overriding automatic replay; normal DI retry settings and legacy ordinary PUT/delete stay unchanged. Interceptors and connection settings remain present. Employee versioned update compares the same token under the EXISTING identity row lock AFTER the unacknowledged recovery-effect gate, then performs the existing mutation/commit. The existing recovery lock order remains unchanged. Neither path establishes cross-row email uniqueness or a schema migration. Every writer that changes the row without rotating its concurrency stamp remains a separate correspondence limit.

Original UserManager/EF Identity uses optimistic ConcurrencyStamp checking ([Identity8.0.3 IdentityUserContext](https://raw.githubusercontent.com/dotnet/aspnetcore/v8.0.3/src/Identity/EntityFrameworkCore/src/IdentityUserContext.cs)); the additive versioned consumer route makes that stale-edit boundary explicit without exposing its stamp. This adaptation is not an exact original wire route or whole UserManager compatibility claim.

Two new real Production HTTP/PostgreSQL cases (one per store) inspect the safe projection/ETag, verify anonymous401/service403/missing-header428/missing404/wildcard412/matching-version invalid400 and actual disabled-recovery503 before reenabling the fixture option, hold an external row fence, observe BOTH real matching-version HTTP writes blocked in PostgreSQL before release (clearing the activity snapshot), then require exactlyone204/one412, reject a subsequent stale edit without changing ANY identity/receipt/effect/action/session row, and confirm the returned version changed and the real credential hash still verifies. The existing validation five, reset four, authorization suites and all previous foci remain required with full780/zero skips and raw/static checks. No consumer should ship from a draft pin; after acceptance the Intranet owner must use this explicit route/version and independently prove its DTO/401/403/400/404/412/428/503/success UX. Business profile email updates are not automatic identity synchronization.

A transient acknowledgement loss after a real write or commit must return generic503, never retry the conditional operation and misreport its own committed change as stale412. No durable operation receipt exists for these conditional writes, so a changed row is not inferred as successful ownership. Two additional real PostgreSQL controls inject a transient Npgsql exception AFTER the customer's actual one-row autocommit update and AFTER the employee's actual transaction commit. They require503, exactlyone execution/committed write, unchanged configured normal retry policy, observed database changes and preserved hash/ID/counter. A separate explicit stale retry is412 and leaves the committed snapshot intact; callers must refresh after an uncertain503. Caller cancellation remains original and is not classified as a guaranteed rollback. No live provider/DB use; full780/focus9/reset4 remain unexecuted forecasts until native CI.
