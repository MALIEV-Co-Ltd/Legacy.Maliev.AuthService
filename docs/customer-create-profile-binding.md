# Customer creation profile binding

Source proposal against accepted Auth main `212b6df4d6c16d33b9ace2d21c075074f7a8ccca`; native acceptance is pending.

The original Customer controller at monorepo `6c1a4921b3524dd575cab5b1f4aa5774ad9b8997` selects the stored customer before creating its identity. It copies `Email`, `Telephone` to `PhoneNumber`, `Fax` to `FaxNumber`, and `Mobile` to `MobileNumber`. This proposal restores that selection in Auth administration while retaining the incoming username, password, confirmation and bootstrap classification.

Direct creation uses the selected profile before beginning its identity write. Operation-keyed creation checks the existing receipt first, then checks again under the existing operation lock. Only when neither receipt exists does it read the profile and bind the new identity fields. Canonical email ownership checks use the bound email. The receipt still hashes the original submitted request with the same PascalCase serialization, PBKDF2-SHA256/210000/32, salt, service subject, operation key and database-id association. Replay and conflicting raw submissions never acquire a profile dependency, including when the profile drifts, disappears or is unavailable. No receipt, schema, update or recovery contract is changed.

The reader uses only configured fixed `Services:CustomerService:BaseUrl`, HTTPS in Production, Auth's separately signed `service:legacy-auth` workload, and the existing `legacy-customer.customers.read` permission. Incoming creation/reconcile permissions remain enforced by their existing authorization path. No incoming bearer is forwarded and no global permission grant is added. The workload credential and explicit existing read grant are deployment prerequisites; missing read authority fails closed before any new identity effect. The reader is not a write authority.

The existing Customer GET `/customers/{id:int}` uses the current resource-read permission and a fresh repository projection. The reader validates exact PascalCase `Id`, `Email`, nullable/omitted `Telephone`, `Fax`, and `Mobile`, rejects duplicate or mis-cased binding fields, and enforces the producer PostgreSQL varchar(256) bounds by Unicode scalar count. A verified missing profile returns generic 404; unavailable or malformed authority returns generic 503. Response bodies are limited to 32 KiB, requests have a ten-second transport deadline, redirects and retries are disabled, authorization headers are redacted, and the own JWT is rechecked after headers and body.

The test-only Customer API join pins accepted Customer main `4eedecd81d1d8dcb4f38d8f76e51e7e9cb2110be` (fresh 385 acceptance). Auth's unchanged Defaults `7edcd961024868513fd5f373cab3dcb261197f77`, Contracts `78e48ffc4ee000df0510cba5e7c7a3c4c4d539d7`, and Workflows `e3a6093324a24968876782153286f52db8b29fd8` remain pinned. Customer's standalone acceptance used inherited Defaults `086760fa`; it does not accept this joined graph. New tests retain actual Auth login/refresh/service-login, signing, reader and PostgreSQL persistence, and actual Customer Production host, JWT validation, resource-read policy, application projection and PostgreSQL data. Only adversarial downstream response cases control the transport. Existing infrastructure tests use explicit stored-profile fixtures and do not claim normal-host boundary acceptance.

The two services do not share an atomic transaction: the verified profile may change after the read, as with the original source's one-read behavior. The existing Customer policy's standard-versus-live enforcement semantics are preserved; no new incoming CustomerRead requirement, live-IAM bypass or inferred production grant is introduced. Hosted Release build, focused cases, full suite, raw coverage, existing evidence readers, formatting/security and offline EF checks must all pass before acceptance. No consumer repin, deployment, live IAM/data mutation or LINE retirement is included.
