# Private host startup failures

Auth wraps the complete host entry point, beginning with `WebApplication.CreateBuilder` and ending with `RunAsync`, in `Maliev.Aspire.ServiceDefaults.Diagnostics.PrivateStartupBoundary.RunAsync`. Existing middleware order is retained. The built-in `AddOpenApi("v1")` registration follows the shared versioned registration so this assembly's generated XML comment transformers participate in the served document.

CI and the container build consume ServiceDefaults commit `7edcd961024868513fd5f373cab3dcb261197f77`. CompatibilityContracts remains pinned to `78e48ffc4ee000df0510cba5e7c7a3c4c4d539d7`. The host uses the shared boundary rather than adding a separate Auth failure formatter.

When host initialization throws, the boundary emits fixed private metadata: EventName `StartupFailure`, Operation `HostInitialization`, Critical severity, event ID5102, and exception type. It sets exit code1 without emitting the exception message or stack trace. Required runtime settings remain required. This boundary does not replace request exception handling, correlation, authentication, readiness or rate limiting.

The process acceptance test launches the actual production entry assembly in Production with a minimal environment allowlist and no inherited runtime configuration. Missing CORS settings exercise a real initialization failure before a database or HTTP request. Assertions require exactly one private failure event, a failing exit code, and absence of raw exception stacks and sensitive configuration identifiers. Fixed diagnostics from configuration validators may still precede the private event.

The original producer pin and unwrapped host were observed failing this test after a zero-warning/error build. The repaired host and accepted producer pin passed the process regression plus existing shared logging consumer tests. Full affected-suite, raw per-production-assembly coverage, static checks and exact-head/post-main CI remain required before this slice is accepted or merged. These focused results do not close unrelated XML documentation, LINE actor/session or shared consumer source obligations.

The required CI workflow additionally collects the full test project's raw coverage using `eng/coverage.runsettings` and applies `eng/Assert-OwnedCoverage.ps1`. The settings select all four owned production assemblies, retain all reported generated source and automatic property accessors, and supply no file, assembly or attribute exclusions. Coverlet6.0.4 still applies its built-in instrumentation behavior, including supported exclusion attributes and some generated constructors; this does not guarantee instrumentation of every physical source line. The checker verifies that every generated EF migration designer and model snapshot file in the owned source inventory appears with measured lines in the fresh Infrastructure report.

The checker computes unique reported source-file/line coverage separately for each assembly and requires at least80% in each; unavailable, missing, duplicate or foreign assembly reports fail. Test collections run serially to limit local/container resource overlap.

VSTest can retain a byte-identical copy of the collector report in its TRX attachment directory. Report selection accepts these identical aliases as one measured report and rejects differing reports without combining their coverage.

CI runs in-repository checker and evidence-export controls. It retains only repository-relative coverage metadata, test method outcomes/counters and checker results for3days. Exported TRX omits raw test output, failure messages and theory parameter values. Distinct physical source paths must not collapse during normalization; export fails on collisions and compares each owned assembly's unique covered/total line counts before and after normalization. These controls validate the checker/exporter, not the application's actual coverage.

Registered HTTPS tests exercise the actual host's OpenAPI document and Google employee exchange endpoints. OpenAPI assertions compare served summaries with compiled API XML, retain public camelCase request/response contracts, and require the documentation route to remain unavailable in Production. A reached HTTP regression observed the login summary missing before the built-in registration was added.

Google tests retain normal JWT authentication, permission handling, MVC, the application exchange coordinator and the production RSA issuer. Only upstream nonce/Google validation/employee lookup/session storage interfaces are controlled. Assertions cover denied callers, input validation, public error mapping, upstream timeout redaction, nonce replay, hashed refresh persistence before issuance and persisted employee sid binding. They do not prove live Google transport or durable PostgreSQL exchange persistence.

Validation uses the shared dotnet-validate action at `e3a6093324a24968876782153286f52db8b29fd8`, including its fail-closed current-tree credential scanner. Unused synthetic fixture passwords are omitted; cleanup privacy fixtures generate per-test canaries and assert their exclusion from reports. No scanner exceptions, coverage exclusions or authorization changes are introduced by this adoption.
