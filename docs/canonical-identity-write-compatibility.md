# Canonical identity writes with retained recovery and receipt frames

This draft is based on accepted Auth1525a0ecba364fe79a4c0e795d04252243d111bc42d. It restores the pinned Identity8.0.28 default NFC-before-invariant-uppercase key behavior for explicitly requested administrative create/update effects. Raw supplied email remains trimmed but otherwise unchanged. The ASCII alphabet for new usernames remains unchanged. Existing rows are not bulk repaired; an explicit successful edit changes only its selected identity and rotates its existing security/concurrency state.

A two-key equality check misses old decomposed or partially composed uppercase-only keys when a new caller supplies the precomposed form. The shared ownership guard first checks indexed canonical and exact retained keys, then streams only identity id/raw value/normalized value for noncanonical or missing-key candidates. PostgreSQL IS NOT NFC NORMALIZED is the predicate; .NET performs invariant key comparison, without database-locale upper/lower or NFKC folding. The fixed unmapped SQL projections fetch no password hashes, stamps, receipts or whole identity rows. The native PostgreSQL18 fixture requires and checks UTF8. The predicate can scan the identity table; this is a correctness guard, with provider command timeouts and cancellation, not a production throughput or arbitrary corrupted-data proof. References: https://www.postgresql.org/docs/18/functions-string.html and https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-8.0/whatsnew#raw-sql-queries-for-unmapped-types.

Participating writers share transaction advisory partitions for canonical email and username. Customer creation, registration and resolve coordinate profile ownership; keyed customer creation additionally coordinates the original service subject/operation key. Existing-row writers lock the selected identity before target key partitions, then check ownership under those locks. Customer conditional update retains its exact version comparison/CAS and uses a fresh nonretrying context with the configured interceptors. Its existing acknowledgement-loss test now injects after the real transaction commit, retaining the same503/one committed effect/no retry/stale412 assertions. New unversioned customer uncertainty maps to a generic503 and has its own normal Production HTTP control. No retry or key recomputation turns an uncertain creation into an owned replay.

Customer create replay remains receipt-first and hashes the unchanged raw JsonSerializer request with the original salt/PBKDF2 frame. An equivalent but differently spelled email in the same operation request is a changed payload and conflicts. Reconciliation reuses the owned context, including a one-connection-pool control. Employee recovery lookup accepts canonical and exact retained keys, but new challenge hashes bind the selected row's exact persisted NormalizedEmail. Existing BoundNormalizedEmail, token:stamp:email hashes and committed recovery effects are never recoded. The customer ceg1 raw-email generation function and raw EmailMatches ownership function remain byte-identical. Customer email-change validation denies a pending historical collision before the caller's profile effect; completed history retains its existing replay path. The final identity effect rechecks the current generation under the identity lock before consuming the challenge. This does not establish cross-service CRM atomicity or deploy readiness.
