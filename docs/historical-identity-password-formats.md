# Historical Identity password-format boundary

Original `Maliev.AuthService.Api/IdentityExtensions.cs` at `5fac706a7983a6d359b39acbd670e6800afe020e` registers the framework password hasher and UserManager. Its identity project references Identity 8.0.3. Current Auth registers the normal framework `PasswordHasher<LegacyIdentityRow>` and its read-only credential reader explicitly accepts `SuccessRehashNeeded`. This is a bounded password-format adaptation, not the whole original UserManager/SignInManager lifecycle or evidence of the original database's actual stored formats.

Four normal Production HTTP cases cover customer and employee identities with independently constructed synthetic Identity V2 and V3 SHA256/10,000 payloads. Both use salt bytes `00..0f` and the existing synthetic fixture password. Python's PBKDF2 independently constructs the fixed base64 vectors; the actual registered current framework hasher must classify each as `SuccessRehashNeeded`. [The pinned framework parser](https://github.com/dotnet/aspnetcore/blob/v10.0.12/src/Identity/Extensions.Core/src/PasswordHasher.cs) specifies the V2 marker/salt/subkey and V3 big-endian PRF/iteration/salt-length header. Default current V3 uses SHA512/100,000.

Each case first sends a wrong password through the actual JSON login route and asserts 401, no credential/hash/token echo, and no session/action writes. Explicit interactive attempt accounting now allows only the selected row's AccessFailedCount, LockoutEnd and ConcurrencyStamp to change. Correct credentials reset a nonzero count and issue a live-validated actor token and one session bound to the exact identity kind/subject/refresh-token hash. Every other mapped field in both identity rows, including hashes and security stamps, remains unchanged; no implicit rehash is written. Normal password validation, token issuance, bearer validation and PostgreSQL stores remain registered. The existing fixture's external Google verifier is unchanged and unused by these cases. See [the accounting contract](interactive-password-attempt-accounting.md) for this deliberate replacement of the former whole-row HTTP immutability assertion; direct reader tests remain read-only.

The workflow retains a dedicated sanitized four-case TRX without parameters, output or failure text. Native outcomes must be inspected before acceptance. No runtime, factory, provider, dependency pin, live identity data, SQL migration, or historical source closure changes in this slice. The separate design-time CLI probe and real schema migration tests remain separate evidence boundaries.
