# Employee identity creation uses the selected persisted profile

The original controller at maliev-web 6c1a4921b3524dd575cab5b1f4aa5774ad9b8997 loads Employee.FindAsync(id), returns 404 when absent, and replaces the submitted identity DatabaseID, Email and PhoneNumber with that employee's fields. A positive identifier alone does not establish this ownership. The current Intranet creates the profile first and passes its returned Id to Auth, but its identity request still carries the original browser email and phone. Auth must enforce the binding even for another authorized caller.

Auth POST /auth/v1/employee-identities/{databaseId} retains its create permission and initial password/username policy. It reads GET /employees/{databaseId} from the configured EmployeeService origin using Auth's separately authenticated service:legacy-auth workload token with legacy-employee.employees.read. The selected PascalCase Id must match exactly. Email and nullable or omitted PhoneNumber come from this profile response; submitted UserName, Password and EmailConfirmed retain their existing semantics. Missing profile returns 404; unverified authority, wrong identifiers, malformed or oversized responses and transport failures return generic 503 before any identity mutation. The existing canonical ownership/transaction rules still determine conflicts after binding.

The transport uses the existing Auth service-token provider and independent own-token validation, a fixed configured HTTPS origin, no redirects or retries, no cache, ten-second deadline, cancellation and 32 KiB response limit. No incoming employee or browser token is forwarded. No global grant is added: deployment needs an explicitly configured legacy-auth workload credential and the existing Employee read permission. Missing configuration fails closed for creation, without requiring production credentials for normal host startup or offline EF tooling.

Normal Production Program tests keep the real token exchange, issuer, own-token verification, HTTP profile client, controller and PostgreSQL identity writer. Only the external Employee profile transport is controlled; snapshots are seeded separately from submitted identity bodies. Permission-isolation tests explicitly use a profile stub. This is a controlled Auth boundary proof, not a running Employee-service, live IAM, cross-service atomicity or deployment proof. A profile may change after the read; this restores the original one-read binding and does not claim a distributed transaction.

Persisted phone values retain the producer's supported lengths, including 65 and 256 characters beyond the submitted identity request's 64-character annotation. The reader uses the Employee producer's actual 256-character schema bound, with a 257-character malformed-producer control; the entire response remains bounded to 32 KiB. This preserves copying from the normal Employee producer whose phone field is not narrowed by its upsert DTO.
