## Implemented bounded worker scan contract

1. Preserve the existing worker's15second scheduling,30second deadline and default-off policy. Perform full read-only readiness before scanning. Cancellation and readiness/query-global failures propagate; no false successful delivery result.
2. Use stable keyset order `(AppliedAt, ActionId)` and a32-receipt attempt budget per invocation. Maintain a worker-process scan cursor across DI scopes, not an OFFSET into a changing pending set. Advance past every attempted receipt, including failed ones. When no rows remain beyond cursor, wrap to the beginning. No deletion, dead-letter authorization, stamp alteration, database lease or new durable table.
3. Cursor is scheduling state only, never recovery authority. An immutable batch high-water tuple bounds each traversal; newly arriving receipts are included next traversal. Ties use ActionId. Every finite pending set is visited across bounded invocations even when its first page is invalid. Restart loses cursor and may repeat already attempted failures, but cannot repeat credential effects; eventual fairness assumes a worker remains alive long enough to traverse the finite set. Continuous unbounded arrival or repeated restarts is not a guaranteed bounded-time liveness claim.
4. For each selected receipt, use a fresh Auth transaction/execution strategy and identity-scoped coordinator exactly as today. Validate exact immutable binding before finalization. Isolate a receipt-local failure only after unwinding its transaction/context; never share failed EF state with the next receipt. Preserve cancellation checks before and after each attempt and during cleanup. Worker never holds an identity lock while acquiring Auth state.
5. After confirmed Auth finalization, attempt employee acknowledgment independently. Any uncertain COMMIT/teardown/ACK leaves the receipt pending. A later visit freshly verifies the durable exact action/receipt markers and acknowledges; it cannot hash a password, rotate stamps or revive a deleted identity. Existing generation-bound employee-only/NULL legacy revocation remains unchanged.
6. Return the count of confirmed acknowledged deliveries. Local invalid/faulted receipts contribute zero and remain pending. Emit only bounded generic failure/count diagnostics, never subject/email/token/password/hash or provider exceptions. Shared infrastructure outage is not reported as every receipt delivered; repeated zero-progress can retain existing generic worker warning.
